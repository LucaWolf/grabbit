# grabbit Remediation: Severe-Fix Audit and Bounded Fix Plan

* **Author:** LucaWolf
* **Date:** 2026-11-22
* **Compilation basis:** assembled from the orchestrator's synthesis instructions with every cited `file:line` re-verified directly against this repository. A reconciliation pass then supplied verbatim, from the lens reports, the three items the initial compile could not read — fix 4's content, the comprehension report's ten open gaps, and the canonical S0–S8 staging — and every citation in them was re-verified against the repo before incorporation below.

## Overview

The driving question was: *is grabbit's intended design broken badly by existing functionality — are severe fixes required?* The answer the six lenses converged on is **no**: the intended design (managed clients owning their recovery, lossy advisory events, recreate-all topology, deferred publish confirmations) is not badly broken, and no architectural rewrite is required. The audit's severe-fix candidates reduce to one already-decided behavioral deviation (topology recovery skipping durable elements), one latent goroutine leak that needs a small code guard, one genuine lifecycle decision (what happens to in-flight confirmations at termination), one event-semantics decision, and a set of mechanical sweeps and doc repairs.

That verdict carries four qualifications, and the plan is not honest without them:

1. **Nothing is verified automatically today.** The Test-and-Coverage workflow triggers on push to `master` (coverage.yaml:4) while this repository's branch is `main` (.git/HEAD:1), so it never fires; it can only be started by hand (workflow_dispatch, coverage.yaml:5), and even then it runs `go test -tags test_env -coverprofile coverage.out -v` with no package pattern (coverage.yaml:17), covering only the root package. The only workflow that runs on `main` is CodeQL static analysis (codeql.yml:16-19), which runs no tests. Until the CI repair lands, no fix in this plan is machine-verified — which is why the author promoted the trigger repair to the plan's first step (Pre-S0, settled 2026-11-22).
2. **Conversion B hides a latent goroutine-leak window.** The connection recovery loop retries notifier setup with `time.Sleep` and `continue`, without any context check (connection.go:198-204). Documenting that FIXME away would leave a leaked goroutine; this needs a code guard, not documentation.
3. **The confirmation lifecycle at termination is the one genuinely architectural decision this plan must make.** `Close` discards in-flight confirmations with two unfixed FIXMEs in line (channel_safewrappers.go:32, channel_safewrappers.go:38), and recovery discards them with no marker at all. The lenses disagree on the semantics, and the options differ in API contract, not just code. Settled in the iteration round — documented-discard, grounded in the dependency's own resolution guarantees (see qualification 4 and the Settled block).
4. **Three of the five items the audit filed as severe (fix 2, fix 3, and observation B) were decision-gated when this brief was compiled.** All three have since been settled in the iteration round — documented-discard for fix 2, Err-only-on-failure for fix 3, and minimal-guard-plus-honest-ADR for observation B. See their Settled blocks; nothing in this plan remains decision-gated.

The audience is the sole maintainer; the library has few users and the author has already authorized breaking changes. The core value of this brief: it separates what is executable now from what needed author decisions — all since made — and puts `file:line` evidence on every claim so `/egm-draft` can verify it later. One engine note frames every broker-behavior claim: **CI's broker is LavinMQ** (container_setup_test.go:137, `cloudamqp/lavinmq`) — and per the author's settled engine decision (2026-11-22), LavinMQ is the *primary* engine, so the suite tests the deployed target directly. RabbitMQ compatibility is best-effort: RabbitMQ-specific claims rest on protocol documentation and folklore comments, not on this repo's test runs, and ADR-0007 (staged with the doc conversions) records the inversion.

## Analysis

### 1. The verification gap comes first

The CI workflow's trigger names `master` (coverage.yaml:4); the repository is on `main` (.git/HEAD:1). The workflow never starts on its own. The test command inside it omits the package pattern (coverage.yaml:17), so a manual run would still skip `internal/traceutils` and every non-root package. AGENTS.md:9 compounds this by claiming "CI uses this exact command" for a `./...` variant that the workflow does not contain. The second workflow, CodeQL, does run on `main` pushes and PRs (codeql.yml:16-19) but performs static analysis only — it compiles for analysis, never runs the test suite. The audit's verdict and every fix below are therefore unverified by automation until the CI repair lands (stage S8 in the canonical staging, with the `master`→`main` trigger repair as its true prerequisite — the zoom-out lens argued for promoting that trigger fix ahead of the baseline, and the staging section records that open ordering call). Related, and reframed by the author's settled engine decision (2026-11-22): the broker in the container test harness is LavinMQ (container_setup_test.go:137) — now the *primary* engine, so the suite validates the deployed target directly rather than standing in for an untested RabbitMQ. RabbitMQ-specific claims (the prefetch-size non-implementation) remain protocol-documentation and folklore grounded (publisher_options_test.go:117; consumer_test.go:421), and ADR-0007 records LavinMQ-primary / RabbitMQ-best-effort so the RabbitMQ-first wording in existing docs (README, publisher_options.go:88-90 on `WithImmediate`) is deliberately superseded, not overlooked.

### 2. Topology recovery skips durable elements — decided, executable (fix 1)

During recovery the channel re-declares only non-durable elements: `if !t.Declare || (recovering && t.Durable) { continue }` (channel.go:336). ADR-0003 accepted the recreate-all contract and records this code path as a pending deviation (docs/adr/0003:24-28), with the deliberate trade-off that a drifted durable definition surfaces as an AMQP 406 precondition failure instead of silently continuing (docs/adr/0003:17-22). Two doc surfaces still describe the old behavior and must move with the code: README.md:32-33 ("during channels recovery (ephemeral queues/exchanges only)") and docs/adr/0001:5 ("ephemeral topology re-declaration"). Removing the branch leaves `makeTopology`'s `recovering` parameter dead (defined at channel.go:320, sole caller channel.go:299, no other use), so the parameter removal folds into the same change. The test surface: channel_topology_test.go runs with `DURABLE = false` (channel_topology_test.go:19) and its topology-count assertion (channel_topology_test.go:219) is the pin fix 1 flips test-first — set `DURABLE = true`, observe the failure at :219 against the current code, apply the channel.go:336 change, observe green. The author has settled the contract; this item is executable now.

### 3. The confirmation lifecycle at termination — the one architectural decision (fix 2)

`Channel.Close` closes the base channel and then cancels the context, with the gap marked twice in the same function: `// FIXME await all confirmations` (channel_safewrappers.go:32) and `// FIXME consume all confirmations` (channel_safewrappers.go:38). In-flight deferred confirmations are neither awaited nor drained. Recovery has the same discard with no marker: `rebase` swaps in a new base channel (channel.go:247-280) and pending confirmations from the old base are left to the amqp library's teardown — grabbit neither resolves nor reports them. A caller holding `AwaitDeferredConfirmation` (publisher.go:94-117) can receive an outcome that reflects teardown rather than a broker decision; the adjacent FIXME at publisher.go:105 asks exactly this and is answered by the dependency source in the Settled block below — the old channel's shutdown resolves pending handles as synthetic nacks on recovery. The lenses did not agree on the semantics, and the disagreement was over an API contract; the author has since settled it (documented-discard, grounded in the amqp091-go facts — see the Settled block). Everything else in this plan is smaller than this decision was.

### 4. Event semantics and noise (fix 3)

`defaultPayloadProcessor` raises `EventMessageReceived` on every processed batch with a fixed payload string in the error field: `Err: SomeErrFromString("default processor discards messages")` (consumer.go:17-22). That string is false on the ack path, where the messages are then acknowledged (consumer.go:24-26) and the `Ack` error return is ignored. The publisher twin raises `EventMessagePublished` on every confirmation with the delivery tag and Ack value packed into `Err` (publisher.go:44-54), contradicting its own doc comment, which states it fires "If confirm.Ack is false" (publisher.go:40-43), and carrying the noise FIXME in line (publisher.go:45). Both raise through a notifier that is unbuffered by default (connection.go:68-73, `make(chan Event)`) and lossy by design (events.go:62-68; docs/adr/0002) — so the per-batch chatter is mostly dropped unless the caller supplied a buffered channel and drains it continuously. The lenses proposed four designs; the author settled it — Err only on failure (see the Settled block). The noise-policy sub-decision (including whether the unbuffered default survives) is separable and deferrable.

### 5. A goroutine-leak window in the connection recovery loop (observation B / conversion B)

In `Connection.manage`, the recovering branch retries `notificationChannels()` on failure with `time.Sleep(conn.opt.delayer.Delay(3))` and `continue` (connection.go:198-204). That branch never checks `ctx.Done()`; the context case (connection.go:215) is reachable only after notifier setup succeeds. If the context is cancelled while the base connection is unset — `Close` before first establishment, or cancellation during recovery after the base was reset (connection.go:222) — the manage goroutine spins indefinitely: a leaked goroutine. The in-code FIXME proposes "adopt a circuit breaker policy" (connection.go:201). The channel-side twin of this loop does not have the hole: its failure path runs through `recover()` into `reconnectLoop`, which observes the context via `delayerCompleted` (channel.go:148-161; channel.go:303). Two existing statements about the backoff mislead and any ADR here must reconcile them: "retry cap of 7 attempts" (general_options.go:32) and "capped at 7–10 attempts" (AGENTS.md:37). `RetryCap` clamps the delay exponent, so the delay saturates at `base * 2^(cap-1)` while attempts stay unbounded (general_options.go:41-52; the retry counter wraps at 0xFFFF, channel.go:291). The verdict's second qualification settles the direction: a code guard is required; converting the FIXME into documentation would hide the leak. The guard's shape and the ADR's wording were settled in the iteration round — minimal guard plus an honest per-loop cadence table (see the Settled block).

### 6. Mechanical sweeps and hygiene (fix 5, conversions A and C, fold-ins)

Fix 5's removal set spans three surfaces: `SafeBool`, exported but referenced by nothing else in the package (events.go:9-12; CONTEXT.md:126-127); the four deprecated `AwaitAvailable` methods (connection.go:35; channel.go:36; publisher.go:194; consumer.go:75); and the deprecated `QueueInspect`, whose sweep carries the traceutils twins.

`QueueInspect` is deprecated in grabbit (channel_safewrappers.go:88-100, deprecation note at :90) and wraps the deprecated amqp091-go method; it keeps a full traceutils twin set — nop (trace_params_nop.go:96-98), testing (trace_params_testing.go:263-267), and the params struct (trace_parameters.go:58) — plus a dedicated test (channel_safewrappers_test.go:143-164), while `QueueDeclarePassive` (channel_safewrappers.go:103) is the supported path. The no-wait confirm hazard survives only as test folklore: "true blocks the amqp Confirm operation" (publisher_options_test.go:117) — and the mechanism is now source-verified rather than folklore: amqp091-go's `Channel.Confirm` unconditionally waits for a `confirmSelectOk` reply (dependency channel.go:1727-1740) while `noWait=true` instructs the broker not to send one, so the call deadlocks client-side, deterministically; the confirmation call site is channel_notifiers.go:38, which passes `ConfirmationNoWait` straight through. The reworded comment can cite this mechanism directly, with no engine-hedging required. The prefetch-size hazard is likewise folklore: "avoid using it, any non-zero will block" (consumer_test.go:421). AGENTS.md already warns about both behaviors, but the evidence base stays buried in test comments. One more drift: the example `examples/publisher_await_delivery` carries a local 4-value `ConfirmationOutcome` enum (confirmationoutcome_string.go:11-14) against the root package's 6 values (publisher.go:13-20) — it lacks `ConfirmationDisabled` and `ConfirmationPrevious`, and its linecomment for the closed case ("data channel is closed") differs from the root's ("data confirmation channel is closed").

### 7. A latent append-aliasing bug in both constructors (fix 4)

`NewPublisher` and `NewConsumer` build their channel options with `chanOpt := append(optionFuncs, WithChannelOptionUsageParams(useParams))` (publisher.go:82; consumer.go:56). If the caller's variadic slice has spare capacity, `append` writes the usage-params option into the caller's backing array — a mutation of caller-owned memory. The remedy the codebase-details lens verified: copy first, append last — `chanOpt := append(append([]func(*ChannelOptions){}, optionFuncs...), WithChannelOptionUsageParams(useParams))` at both sites — which preserves order and precedence; the usage-params option must remain last so the constructor's usage params override any user-supplied ones (current behavior). The blast radius is empty in-repo: every constructor call site passes inline variadic arguments, which the compiler materializes as fresh slices, and no in-repo caller spreads a slice with `...` (the codebase-details lens tallied 9 test and 8 example sites). The zoom-out lens adds an optional package-local helper so the pattern cannot regress, and a regression-test suggestion: construct with a spare-capacity slice and assert the caller's array is untouched. Two contract rows become false the moment the fix lands and must move in the same change: the "Constructor appends" invariant (CONTEXT.md:211-213) and the caller-owned-mutations side-effects bullet (CONTEXT.md:234-237).

## Alternatives Weighed

* **Fix 2 — expose a pending-confirmations count API.** Rejected: it adds public API to avoid making the lifecycle decision the FIXMEs actually ask for (channel_safewrappers.go:32, :38); the count is stale by the time a caller reads it, and the silent-discard semantics survive underneath the new surface.
* **Fix 2 — correlate channel state at resolution time to report `ConfirmationClosed` instead of the synthetic NAK.** Rejected by the author (2026-11-22): over-complication without real gain — the correlation is honest at graceful Close but racy across recovery, and the documentation carries the same distinction without runtime cost.
* **Fix 3 — keep raising on every outcome with the result packed into `Err`.** Rejected: it extends the existing success-string-in-`Err` abuse (consumer.go:21; publisher.go:50-52) instead of fixing the field's meaning. It costs less than a new event kind — no stringer regeneration, no doc pins — but it keeps the error field lying on the happy path.
* **Fix 3 — new `EventMessageNAcked` kind (design critic's option), weighed against the above.** Rejected by the author (2026-11-22): cleanest semantics — acks and nacks become distinguishable by event kind without any `Err` use — but its cost is stringer regeneration (eventtype_string.go, eventtype_string_test.go, committed `go generate` output — CI never regenerates), the doc surfaces that enumerate event kinds, and two count pins, for a default fallback callback that serious users replace with their own callback or the deferred-confirmation API.
* **Observation B — a classic circuit breaker.** Rejected: grabbit already gives callers three abandonment controls over the recovery loop — the Down/Recovering callbacks can veto reconnection (callbackAllowedRecovery, general_options.go:157-159; callbackAllowedDown, general_options.go:165-167), context cancellation terminates the loops (connection.go:215; channel.go:168), and the backoff saturates so retries slow to a fixed ceiling (general_options.go:41-52). A breaker would add a second, competing authority over the same loop. The remaining need is a context check in the branch that lacks one, not a new policy object.
* **Release shape — splitting the breaking changes (fix 1's behavior change, fix 5's deprecated-path removal) across multiple releases.** Rejected: with few users and breaking removals authorized, a split prolongs the period where docs and code disagree; one batched breaking release.
* **CI — widening the test command to `./...` alone.** Rejected: the missing package pattern (coverage.yaml:17) is one of four defects. The workflow would still never fire on `main` (coverage.yaml:4 vs .git/HEAD:1), PRs would remain un-gated, and the production build (untagged by `test_env`) would remain compiled nowhere. The structural repair covers all four.

## Key Decisions & Staging for Next Steps

### Settled by the author (recorded, not re-opened)

* **Compatibility policy:** breaking changes are acceptable; the library has few users. Removals (the deprecated `QueueInspect` path, the dead `recovering` parameter) are authorized.
* **Topology contract:** recreate-all per ADR-0003 (docs/adr/0003); the skip-durable branch at channel.go:336 is a pending deviation to remove, not a behavior to preserve.
* **Advisory events stay lossy** (docs/adr/0002) unless the noise-policy decision below says otherwise.
* **Broker engine: LavinMQ primary, RabbitMQ best-effort** (settled 2026-11-22, stated by the author at close-off). The amqp091-go driver is unchanged — all client-side facts in this plan are untouched — but the source of truth for observable integration behavior inverts: CI's LavinMQ container (container_setup_test.go:137) now tests the primary engine directly instead of standing in for an untested RabbitMQ. Record it as ADR-0007 so the RabbitMQ-first assumption baked into existing docs (README, the WithImmediate engine note at publisher_options.go:88-90) is not "corrected" back.

### Settled — fix 2: documented-discard (author's decision, 2026-11-22, after reading the dependency source)

The amqp091-go facts dissolved the drain debate. On any channel shutdown the dependency runs `ch.confirms.Close()` (channel.go:146 within `shutdown`, amqp091-go v1.10.0), and `deferredConfirmations.Close()` — its own doc comment: "Close nacks all pending DeferredConfirmations" — resolves **every** pending handle with `setAck(false)` and fires `Done()` (confirms.go:185-194). So deferred confirmations are never lost at Close or recovery: they self-resolve, deterministically, without grabbit doing anything. The `publisher.go:105` FIXME ("could this be triggered by recovery before the channel's context?") is answered: yes — the old channel's shutdown fires it on recovery. What the drain options would have recovered is only the advisory listener flavor (already-buffered events), non-load-bearing per docs/adr/0002; and the undecided subset — messages the broker had not yet answered — is unknowable by AMQP construction. No design recovers it.

**Decision: documented-discard, zero code.** Both FIXMEs (channel_safewrappers.go:32, :38) are replaced by the contract statement, and the outcome documentation gains the semantic note: a `ConfirmationNAK` seen at or after termination is the dependency's synthetic nack — "channel died before the broker answered" — meaning *fate unknown, not rejected*; at-least-once publishers re-publish and dedup on the consumer side. The declined alternative (correlating channel state to report `ConfirmationClosed` instead of the synthetic NAK) was rejected as over-complication: honest at graceful Close but racy across recovery, for a distinction the documentation carries without runtime cost. No new Close-time test is required — the deferred path's resolution is dependency-guaranteed and behavior-preserving. S6 is unblocked as a documentation change; the amqp091-go close-flush verification prerequisite and the non-negotiable `-race` gate fall away with the drain design.

### Settled — fix 3: Err only on failure (author's decision, 2026-11-22)

Today `defaultNotifyPublish` raises `EventMessagePublished` per confirmation with the delivery tag and ack value packed into `Err` as a string — on successes too — contradicting its own doc comment (publisher.go:40-54).

**Decision: keep the per-confirmation raise; set `Err` only on failure** — the zoom-out lens's two-line variant, confirmed after the `OptionalError` mechanics were laid out. On success the event carries `OptionalError{}`, the zero value: `IsSet()` is false and `Error()` renders the documented fallback "no error" (error.go:9-31). On failure it carries `SomeErrFromString(...)` with the delivery tag and nack. This is not a new convention: `makeTopology` already raises `EventDefineTopology` with `Err` set only on element failure (channel.go:343-365); the confirm event was the library's outlier, and this decision makes it obey the existing pattern.

Side effects, disclosed and accepted: the three consumer_test.go gates (:199, :393, :564 — each a `MsgPublished.ValueEquals(MSG_COUNT)` wait counting raises) survive untouched; no stringer work and no count-pin updates (15 event kinds unchanged); `defaultNotifyReturn` is untouched (a returned message is always a failure — its `Err` stays). The one observable loss: success events no longer carry the string-packed delivery tag — nothing in-repo parses it (the supported per-message outcome path is `PublishDeferredConfirm`), but an external consumer of that string would notice. The lying doc comment (publisher.go:40-43) is corrected in the same change; the noise FIXME (publisher.go:45) stays a deferrable sub-decision governed by docs/adr/0002.

Declined alternatives: **ACK-silent/NACK-only** — matches the doc comment's literal promise, but breaks the three gates and removes positive-publish observability; **new `EventMessageNAcked` kind** — cleanest semantics, but stringer regeneration, the enum-bounds row, and two count pins for a default callback that serious users replace anyway; **doc-comment-only** — leaves `Err` lying on every success.

S5 is unblocked: a two-line change at publisher.go:44-54, the doc-comment correction at publisher.go:40-43, and the CONTEXT.md default-callbacks sync (:214-218).

### Settled — observation B: minimal guard + honest ADR (author's decision, 2026-11-22)

The guard is mandatory (qualification 2): the notifier-retry branch at connection.go:198-204 retries with `time.Sleep` and no context check, so a `Close()` racing that window leaks the manage goroutine. **Decision: minimal guard** — replace the bare sleep with an interruptible wait using the repo's own idiom (the `delayerCompleted` pattern, matching the channel twin's escape at channel.go:148-161), so cancellation always exits the loop. **Plus ADR-0006, written honestly**: recovery retries indefinitely; abandonment is caller-driven (callback veto via `callbackAllowedRecovery`/`callbackAllowedDown`, context cancellation, idempotent `Close`); the backoff saturates — the cap clamps the delay exponent, never the attempts. The ADR carries the per-loop cadence table as the code actually behaves (connection retry saturating, 12.8 s–102 s ceiling; channel rebase pause flat `Delay(1)`, channel.go:303; notifier-refresh flat `Delay(3)`, connection.go:202 / channel.go:159; the 120-second anti-hot-loop timers, connection.go:229 / channel.go:197) and reconciles the two misleading statements ("retry cap of 7 attempts", general_options.go:32; "capped at 7–10 attempts", AGENTS.md:37). It defines "caller-driven abandonment" and "saturating backoff" in repo vocabulary and scopes the guard to the notifier-failure path while describing the general loops' cadences in the same table. Tests that move: a new case cancelling the context before establishment and asserting the manager exits via `AwaitManager`; the goleak harness (container_setup_test.go:185) then catches regressions. Unifying the flat cadences toward the saturating policy was declined as unnecessary code churn now — they are recorded as known behavior.
