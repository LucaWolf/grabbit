## Overview

The 2026-11-22 brief answered the driving question — *is there base fixes pending before any new functionality?* — with a gate block and a feature plan whose concurrency shape was **batch fan-out**: the existing `CallbackProcessMessages` batch dispatched over sub-slices. This edition amends that shape. The feature concept is now **per-record concurrent dispatch**: a per-channel selector (option `WithProcessorConcurrency`, field `ProcessorConcurrency` on `ConsumerUsageOptions`) whose zero value keeps today's batch/sequential path byte-for-byte and whose positive value switches that channel to per-record dispatch — deliveries flow to a pool of that many worker goroutines as they arrive, with no batch fill and no fill timeout. Each worker processes one message and returns a per-record outcome (Ack, Nack(requeue), Nack(drop)), which the library executes as an individual `multiple=false` wire call from one library-owned, status-re-checked place. Batch and record-concurrent consumers coexist on one connection (separate channels); the `QosGlobal` interaction is a documented caveat. The batch hook and the flush events (`EventDataPartial`/`EventDataExhausted`) remain on the sequential path and retire on the concurrent path.

Why the shape changed: batch width is fan-out width. Dispatch happens either at batch fill (`channel_consume.go:85`) or at the flush timer (`:100`), so no timeout value gives both low latency and parallelism — a large batch maximizes parallelism but delays the first item by the fill; a small batch maximizes latency responsiveness but collapses the fan-out. Per-message dispatch decouples the two: concurrency is the pool size, latency is per delivery.

The gate answer carries forward unchanged in all its parts, and the amendment strengthens two of its items. Restated briefly:

* **Blocker — the verification the gate demands does not exist.** No `-race` anywhere in CI (`coverage.yaml:4` trigger is `master` while the branch is `main`; `:17` test command has no race flag and no package pattern; no `.github` workflow contains "race"); the remediation plan staged none (`concepts_brief_remediation_audit.md:133`, `:140`, `:90`). The gate gains S0-R (local race baseline) and an early CI `-race` job — settled 2026-11-22 (DR2). Per-record dispatch adds worker goroutines to exactly the latch-reading dispatch surface (`channel_consume.go:90-94`, `:108-112`), which raises S0-R's value.
* **Blocker — S5 as staged does not touch the feature's surface** (publisher-only; the consumer-side `Err` defect at `consumer.go:21`/`:25` rides no stage). Settled (DR2): the consumer-side correction folds into the feature's F2 stage — under the amended shape, F2 rewrites the consumer default processor entirely.
* **Gate (hygiene) — S1 first** (`publisher.go:82` + `consumer.go:56` copy-first append). The feature's option plumbing flows through `consumer.go:56`; ordering hygiene, not functional dependence.
* **Soft gate — the observation-B guard** (`connection.go:198-204`) before-or-alongside, for goleak attribution: whole-main leak detection (`container_setup_test.go:185`) cannot attribute a pre-existing connection-loop leak versus a feature worker leak at one suite exit.
* **Hard gate — S4 before the feature's recovery-test work** (settled 2026-11-22, test-isolation rationale): the feature's recovery tests declare `Durable: true` topology (as `consumer_test.go:179-184` does) against the pending skip-durable deviation (`channel.go:336` vs `docs/adr/0003:24-28`).

The amendment's six-lens review found the per-record concept architecturally sound — the decoupling rationale holds mechanically against `channel_consume.go:85` and `:100` — conditional on four decisions being settled that the anchor left unstated: the per-record callback's exact surface (the feature's entire public API), the dispatch discipline and its in-flight bound under auto-ack, the ack-issue re-check mechanics, and the worker lifecycle on shutdown and across generations. All four are settled below (DR1, DR3, DR5, DR6), together with the retirement semantics for the batch-path machinery the concurrent path replaces.

## Analysis

### 1. The verification gate (carried forward, unchanged)

The workflow triggers on `master` (`coverage.yaml:4`) while the branch is `main` (`.git/HEAD:1`); the test command has no race flag and no package pattern (`coverage.yaml:17`); CodeQL runs on `main` but performs static analysis only (`codeql.yml:14-21`). The race surface is real and now larger: per-record dispatch adds N worker goroutines per consumer channel, spawned per recovery generation (`channel_notifiers.go:56`), reading the same latch values the manage goroutine mutates (`channel.go:152`, `:170`) and sharing the settle path's latch reads. `flag.Parse()` at `container_setup_test.go:183` already anticipates `-race`; the local command runs against the LavinMQ container (`container_setup_test.go:137`, engine constant `podman` at `:24`). First-ever CI execution after Pre-S0 remains a discovery step for runner issues; a race-enabled broker suite costs several-fold wall time over the already-slow `TestBatchConsumer` (2345-message connection-kill scenario, `consumer_test.go:136-289`).

### 2. Plumbing: the knob rides the embed, the callback rides the optionFuncs (verified end to end)

A field on `ConsumerUsageOptions` (`consumer_options.go:13-26`) reaches the channel with zero `NewConsumer` code change: wholesale struct copy into `ChanUsageParameters` (`consumer.go:53-55`), appended last via `WithChannelOptionUsageParams` (`consumer.go:56`; `channel_options.go:120-128`), read by the consume loops as `ch.opt.implParams.*` (`channel_consume.go:12`, `:56-57`, `:85`, `:100`). A field on `ConsumerOptions` *outside* the embedded struct never reaches the channel (`ConsumerOptions` is a bare embed, `consumer_options.go:28-30`) — the single most likely mechanical mistake, carried forward from the prior brief.

The processor callback travels a different path: it is a `ChannelOptions` field set via `WithChannelOptionProcessor` (`channel_options.go:25`, `:112-118`), not part of the usage params. The new per-record callback therefore also needs zero `NewConsumer` change — but its type and builder belong on the existing callback path (`general_options.go` for the type, `channel_options.go` for the builder, per repo convention: callback types at `general_options.go:62-78`, `:143-145`, `:151`; builders at `channel_options.go:112-118`). This corrects the prior brief's F2 staging, which placed the hook type in `channel_consume.go`. Raw `NewChannel` + `WithChannelOptionUsageParams` users reach `implParams` unconditionally (`channel_options.go:123-128`) — they receive the concurrent model (knob and record callback) for free; documented, not excluded.

### 3. The consumer-side event contract: now rewritten in full

`defaultPayloadProcessor` raises `EventMessageReceived` with `Err: SomeErrFromString("default processor discards messages")` on every batch (`consumer.go:17-22`) — false on the ack path, where it bulk-acks the last tag with `multiple=true` and discards the `Ack` error (`:24-26`). The settled fix-3 convention is Err-only-on-failure, following the `makeTopology` precedent (`channel.go:345`, `:349`; remediation brief `:92-102`). Under the amended shape, F2 defines **two** default processors: the corrected batch default (sequential path) and a new **default record processor** (concurrent path) that returns the Ack outcome per record and raises `EventMessageReceived` with `Err` set only on failure. The pins survive: `MsgReceived` counters count raises, not `Err` content (`container_setup_test.go:607-610`), and the only gate is a tolerant `GreaterEquals` (`consumer_test.go:570`). The CONTEXT.md default-callbacks row (`:214-218`) is triple-booked — S5's publisher half, the consumer Err correction, and the new record default — the staging sequences the edits so no half-corrected row persists.

### 4. Ack ordering: the hazard dissolves by construction on the concurrent path

AMQP `basic.ack` with `multiple=true` acknowledges every outstanding unacknowledged delivery up to the tag on the channel — a definition the repo states nowhere (`GLOSSARY.md:50-62` has no ack entry). The bulk habit survives today only because processing is serialized (one synchronous batch at a time, `channel_consume.go:95`, `:113`). The amended design removes the hazard rather than policing it: record workers never receive a delivery tag to bulk-ack with — the library executes each outcome as `Ack(tag, false)` / `Nack(tag, false, requeue)` from one place (the settle helper, DR1). Worker-issued bulk acks are structurally impossible on the concurrent path, not forbidden by convention. The sequential path keeps today's barrier-then-one-bulk-ack wire pattern unchanged (DR3).

One example-side note feeds ADR-0008: the shipped `examples/consumer` handler already demonstrates the exact per-item pattern the concurrent path enforces (`examples/consumer/main.go:78-80`) — usable as prior art. The serial-only marking applies to the test corpus and the consumer_batch example, not to every example.

### 5. mustAck and the stale-tag hazard: per-record re-derivation, settle-time re-check, pin test first

The batch facts carry forward unchanged: `mustAck` initialized once per gobble (`channel_consume.go:56`), ANDed with a 100 ms `AwaitStatus(true, ...)` and a latch-transition check immediately before each processor call (`:90-94`, `:108-112`), sticky-false for the generation's life, never re-derived; two contradictory `!mustAck` conventions shipped (tests abandon processing, `consumer_test.go:58-62`; default processor process-and-skip-ack, `consumer.go:16-26`; ADR-0004 mandates process-and-leave-unacked, `docs/adr/0004:10-12`). The stale-tag mechanism is verified: `Ack` routes to whatever `baseChan.super` is current under `baseChan.mu` (`channel_safewrappers.go:71-75`), `rebase` installs a fresh super (`channel.go:268`), and the wrapper consults nothing else.

The concurrent path resolves the convention conflict and narrows the hazard, with three pinned rules:

* **Re-derive, don't inherit.** Each record's ack-worthiness is computed fresh from `!ConsumerAutoAck` at settle time; the sticky-false variable is not carried onto the concurrent path.
* **Non-blocking settle-time re-check.** The settle helper re-checks the connected latch immediately before the wire call and skips the call on a transition — the skipped outcome leaves the record unacked, and the broker redelivers (the ADR-0004 duty, executed library-side). Critically, the re-check is *non-blocking*: the batch path's 100 ms `AwaitStatus` probe is unaffordable per record (a degraded link would serialize the pool). **Prerequisite:** the latch `Details()` transition-counter semantics are dependency-internal (go-notifying-latch v1.1.0) and pinned by nothing in this tree — the prior brief's caution (`:57`) carries forward as a staged obligation: a unit test pinning the counter's behavior (including whether the establishment `Unlock` at `channel.go:152` counts) lands as F2's first item, before any code leans on the transitions check.
* **Narrowed, not closed.** A rebase can still land between the re-check and the wire call (TOCTOU against `channel.go:268`); with `multiple=false` an old-generation tag can then hit the new channel's tag space (tags restart at 1) and ack a different record — at-least-once-unsafe for that record, the worst case the design admits. ADR-0008 states "narrowed, not closed"; the closure path (a dedicated mu-scoped check-and-ack wrapper) is recorded as optional hardening in DR3, adopted only if the pinned latch semantics reveal a live window.

Because the record callback receives no `*Channel` (DR1), the raw-`Super()`-in-workers hazard the prior brief worried about (§7, ADR-0008 bullet) is moot on the concurrent path — there is no handle to misuse.

### 6. Worker lifecycle, generations, shutdown

* **Pool per generation, join before return.** The concurrent gobble spawns N workers at the existing spawn point (`channel_notifiers.go:56` — unchanged, per recovery generation) and joins them with a WaitGroup before returning. Workers select on exactly two signals: the deliveries feed and `ctx.Done()`. On feed close (generation end) or ctx cancellation (`Close`, `channel_safewrappers.go:37`), workers exit between records; gobble returns only after the join. The contract "gobble returned implies no outstanding user code" is thereby preserved on the concurrent path in its delayed-by-one-record form — the concurrent analogue of today's synchronous teardown flush (`channel_consume.go:62-75`). Deliveries never received are simply left unacked and redelivered — the same at-least-once outcome as today's `mustAck=false` teardown flush.
* **Recovery does not cancel the channel context — only `Close` does** (`channel_safewrappers.go:37`; verified: the manage loop's recovery path at `channel.go:182-195` resets the base and locks the connected latch but never cancels ctx). Feed close is therefore the load-bearing generation-end signal for workers, not ctx. This nuance is load-bearing for the F3 shutdown tests.
* **The transient 2N overlap carries forward unchanged.** Old-generation workers exit asynchronously; there is no barrier synchronizing old-exit to new-start (`channel_consume.go:69-75`); two generations transiently run 2N workers. The bound is stated per generation in ADR-0008.
* **User-work abort remains impossible** — the callback receives no context (`general_options.go:143-145`); this non-goal is unchanged. A worker blocked in a user callback that never returns delays the join exactly as today's synchronous batch callback can delay gobble's teardown: same exposure, documented, not solved.
* **Shutdown joins nothing at the library level** (`Close` waits for nothing, `channel_safewrappers.go:26-41`) — but the gobble join means goroutine termination is still test-assertable: goleak plus `AwaitManager`/`AwaitConnectionManagerDone` (`container_setup_test.go:153-159`, `:185`) and per-test worker-exit assertions. `wgDoneOrTimeout` self-leaks its waiter on timeout (`:196-209`, comment at `:206`) — feature tests must not reuse it.

### 7. What the parallelism buys, and the serialization point

`baseChan.mu` remains the serialization point: every safe wrapper performs broker I/O while holding the channel mutex (`channel_safewrappers.go:67-75`; `CONTEXT.md:231-233`), the same mutex recovery needs (`channel.go:183`, `:268`). Concurrent worker acks are legal because of that mutex and serialized by it; N workers make N waiters where today there is one. The ceiling test must instrument *processing* concurrency, not ack-call concurrency. The raw-access contract (`CONTEXT.md:208-210`) is not exposed to record workers at all (no `*Channel` parameter — DR1).

The throughput mechanism is now the default rather than a designed option: with the library executing per-item `multiple=false` acks at each record's completion, the broker's prefetch window refills continuously while other records are still processing — there is no batch barrier to stall it. The prior brief's batch-barrier ceiling arithmetic (`PrefetchCount / (slowest item + join + ack round)`) described the sequential path and still does; it no longer describes the concurrent path (see §8).

Verified non-hazard, reshaped: the prior brief's shared-`props`-across-the-batch caution (`:69`) is **moot on the concurrent path** — there are no batches, and each record's properties are computed fresh via `DeliveryPropsFrom` (`general_options.go:97-108`). One residue survives: `DeliveryPropsFrom` copies the `Headers` map reference, not the table (`general_options.go:99`) — record callbacks treat `props.Headers` as read-only, one doc line in the callback's comment.

### 8. The bound and its traps, restated per path

The concurrent path's bound: **in-flight (processing) concurrency is at most `ProcessorConcurrency` by construction** — N workers, one record each. Under manual ack (the default), the broker's prefetch additionally caps unacked deliveries at `PrefetchCount`, so the effective parallelism is `min(ProcessorConcurrency, PrefetchCount)`. Under `ConsumerAutoAck(true)`, the broker applies no prefetch throttle (protocol-level, dependency/broker-internal — the prior brief recorded the batch path's client-side cap as the only bound there, `:73`; per-record dispatch **deletes that cap** along with the accumulation slice, `channel_consume.go:57`), so the pool size is the only grabbit-owned bound. A pool larger than prefetch idles under manual ack — workers park on feed receive; harmless.

Four traps, restated:

1. **Inert at defaults (carried).** `DefaultConsumerOptions` sets `PrefetchCount: 1` (`consumer_options.go:46`) — any concurrency value does nothing until prefetch is raised. WARNING-grade doc on the builder (precedent `consumer_options.go:82`, `:113-115`).
2. **The zero-default flush timer retires on the concurrent path.** `DefaultConsumerOptions` sets no `PrefetchTimeout` (`consumer_options.go:42-53`) and `time.After(0)` fires immediately (`channel_consume.go:100`) — the batch path's hot loop. The concurrent loop has no timer arm at all (DR6), so the trap is deleted per-path rather than documented; the sequential path keeps it as a known trap.
3. **Unvalidated knobs (carried, semantics pinned).** `WithPrefetchCount` accepts zero/negative (`consumer_options.go:76-79`); `PrefetchCount ≤ 0` with a concurrent pool is unsupported and documented as such (no validation — repo precedent). Negative `ProcessorConcurrency` behaves as zero (sequential path), documented in the builder; the `ClampInt` normalization alternative (`utils.go:11-13`) was weighed and declined (no validation anywhere else in the option family).
4. **The QoS trace pin (carried).** `TestConsumerOptions` asserts via the trace harness that `Qos` is called with the exact configured parameters (`consumer_test.go:469-485`; trace at `channel_safewrappers.go:227`, params at `internal/traceutils/trace_parameters.go:17-21`). The library never auto-adjusts prefetch (no `max(PrefetchCount, workers)`), so the pin stays green; the effective window is the broker's to apply.

## Alternatives Weighed

* **Batch fan-out over sub-slices (the prior F2 shape) — superseded.** Batch width is fan-out width (`channel_consume.go:85`, `:100`); no timeout gives both latency and parallelism. It also handed each invocation direct ack authority through `ch *Channel` that the library cannot intercept (`concepts_brief.md` 2026-11-22, §Alternatives). Per-record dispatch replaces it; the batch fan-out machinery, per-batch ephemeral pools, and the `min(knob, len(batch))` caveats are deleted rather than built.
* **User-side parallelism inside the existing callback — remains the recorded no-library-change alternative.** Works today; the join exists at callback-return; broker prefetch bounds outstanding work. Gap: no context accessor on `Channel` (`CONTEXT.md:65-76`), so user workers have no clean abort signal; every project reimplements the pool. Superseded by the author's DR1 decision; retained as the fallback.
* **Bounded work-channel dispatcher (design lens) — declined in favor of worker-pull.** A work channel of capacity N with gobble dispatching via a two-case select bounds read-ahead at N+1 under auto-ack. Declined: the bound the feature must provide (≤ N concurrent callbacks) holds by construction with workers reading the feed directly; the work channel adds a dispatcher select, close protocol, and one more channel to leak-check, for a read-ahead guarantee that the AMQP dependency's internal feed buffering blurs either way (dependency-internal). Recorded so it is not re-derived.
* **Worker-per-delivery (`go worker(msg)`, no pool) — declined.** Concurrency would become prefetch-bounded rather than N-bounded, contradicting the documented contract of the knob.
* **Including `*Channel` in the record callback — declined (recorded disagreement).** Lenses split: exclude (design — including it re-opens the exact cross-worker ack hazard DR1 exists to close, and the exclusion is what makes the ack authority enforceable rather than conventional) versus include-with-documented-forbidden-acks (zoom-out, codebase-details — convention symmetry, publish-from-processor convenience). Resolved to exclusion: a closure captures whatever dependencies it needs (a publisher, a client); the parameter surface stays minimal; the batch hook remains for users who want channel access. The sequential path's raw-access caveats are unchanged.
* **`mustAck` as a callback parameter — declined (recorded disagreement).** Retaining it (zoom-out) would drag the two contradictory in-repo `!mustAck` conventions into the new API; omitting it (comprehension, codebase-details) keeps the surface minimal and moves the ADR-0004 duty library-side. The user learns of a transition through `EventDown` on the notifier channel, not through the callback.
* **Outcome as bool / struct-of-bools / Reject primitive — declined.** A bool leaves drop expressible only by escaping the library's ack authority via direct channel calls; a struct admits invalid states; `Reject(tag, false)` is wire-equivalent to `Nack(tag, false, false)` (`channel_safewrappers.go:56-64` vs `:78-86`) and would add a third code path — the drop outcome executes through `Nack` for a literal single settle site.
* **Outcome-enum stringer — following repo precedent (recorded disagreement).** All three public enums carry stringer output + guard tests (`publisher.go:12-20`; `eventtype_string.go`; `CONTEXT.md:219-221`). Zoom-out recommended three plain constants without a `String()` method to avoid the cost; resolved to follow the precedent (a fourth public enum without the guard would be a half-precedent), with the guard-row edit priced into F1/F4.
* **Ack trace parameters at the settle site — declined.** Would require `ParamsAck`/`ParamsNack` pairs, nop/testing twins, and traceutils contract rows, reversing a twice-settled non-goal. Observability is served by the advisory `EventMessageReceived` and processor-side instrumentation.
* **Validating `ProcessorConcurrency`/`PrefetchCount` at the builder — declined.** No option in the family validates (`WithPrefetchCount`, `consumer_options.go:76-79`); semantics are documented instead (negative = off; `PrefetchCount ≤ 0` unsupported on the concurrent path). `ClampInt` normalization (`utils.go:11-13`) noted as the alternative.
* **Gate orderings and release shape — carried.** S4 strictly before the feature's recovery tests (DR2); S5 publisher-only; the feature as a fast-follow minor (DR4); preceding or riding the batched release remains rejected.

### Settled — DR5 (new): per-channel dispatch-model selection and coexistence

* **Selection:** `ProcessorConcurrency == 0` (or negative) selects the sequential path — byte-identical behavior, including all its traps; `> 0` selects the concurrent path. The model is fixed at construction; no runtime switching.
* **Combination rules:** with `ProcessorConcurrency > 0`, a registered batch hook (`WithChannelOptionProcessor`) is ignored on that channel — documented in both builders' doc comments (the advisory-event alternative was weighed and declined); at `0`, a registered record callback is unused. The default record processor serves the "concurrency on, no callback" case (DR1).
* **Coexistence:** batch and record-concurrent consumers run on one connection as separate channels — no shared state beyond what channels already share; nothing in the coexistence requires connection-level changes.
* **Raw-channel exposure:** raw `NewChannel` + `WithChannelOptionUsageParams` receives the knob and the concurrent model unconditionally (`channel_options.go:123-128`); documented, not excluded.
* **QosGlobal caveat (wording settled):** "`WithQosGlobal(true)` widens the QoS window's scope beyond this channel's own consumers — under AMQP global semantics the window is shared across the connection's channels, so a concurrent consumer's pool sizing draws from a budget every sibling channel competes for. The interaction is untested in this repo (`consumer_test.go:424` exercises global QoS with a single consumer) and its exact scope is engine-dependent (LavinMQ-primary per ADR-0007, RabbitMQ best-effort). Keep `QosGlobal(false)` — the default — when mixing batch and record-concurrent consumers on one connection. The `Qos` call always receives the configured parameters (trace pin, `consumer_test.go:469-485`)." The misleading field comment "all future channels" (`consumer_options.go:19`) is corrected in F4.
  * **Correction (T13, 2026-11-25):** RabbitMQ documents global QoS as **per-channel**, not connection-wide, and deprecates/disables it from 4.3. ADR-0008 records the corrected caveat: grabbit consumers each own a channel, so `QosGlobal` cannot widen the bound.

### Settled — DR6 (new): concurrent-path mechanics and the retirement set

* **Dispatch discipline:** workers pull directly from the deliveries feed — no dispatcher goroutine, no internal work channel. Processing concurrency is bounded by N by construction; under manual ack, in-flight unacked records are additionally bounded by `PrefetchCount` (effective parallelism `min(ProcessorConcurrency, PrefetchCount)`); under `ConsumerAutoAck(true)` the pool size is the only grabbit-owned bound (the AMQP dependency's feed buffering is dependency-internal). The concurrent loop's select has exactly two cases — the feed and `ctx.Done()`.
* **Retirement set on the concurrent path** (what the option deletes): batch fill and the accumulation slice; the `PrefetchTimeout` timer arm (`channel_consume.go:100`) — set-but-ignored, no timer armed, which also deletes the zero-default hot loop on this path; `EventDataPartial`/`EventDataExhausted` (never raised, `:100-121`); the sticky `mustAck` variable (`:56`); per-batch props sharing. There is no queue-drain event on the concurrent path — completion gating is registry-based (`SafeRegisterMap`); documented in ADR-0008 as a contract difference from the sequential path.
* **Poison-message contract:** a record returned with `RecordNackRequeue` redelivers immediately (protocol-level) — per-record dispatch removes the batch cadence that incidentally throttled the loop, so a poison record spins at wire speed, occupying one worker and one prefetch slot, flooding the lossy event channel. The library performs no retry counting, no backoff, no suppression (decision, not omission); processors detect the loop via `DeliveryData.Redelivered` (`general_options.go:117`) and route to `RecordNackDrop` or fix the payload upstream; dead-letter-exchange guidance is broker documentation (LavinMQ-primary caveat). ADR-0008 carries the paragraph; the builder doc carries the WARNING; F3 proves the loop is finite when the callback stops requeueing and that goroutines do not grow.
