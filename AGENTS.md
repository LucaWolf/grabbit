## Developer Commands

- `go test -tags test_env -coverprofile coverage.out -v ./...` — run all tests with tracing enabled (the `test_env` build tag activates trace instrumentation; without it, trace functions are no-ops). CI uses this exact command (`.github/workflows/coverage.yaml`).
- `go test -race -tags test_env ./...` — run tests with the race detector.
- `go build ./...` — build the package.
- Coverage report is generated by the `ncruces/go-coverage-report` action after tests complete.

## Package Boundaries & Entrypoints

This is a single-module Go library (`github.com/LucaWolf/grabbit`, Go 1.25.7). The four primary types are the main entrypoints:

- **`NewConnection(address string, config amqp.Config, optionFuncs ...func(*ConnectionOptions)) *Connection`** — create a managed RabbitMQ connection with auto-reconnect.
- **`NewPublisher(conn *Connection, opt PublisherOptions, optionFuncs ...func(*ChannelOptions)) *Publisher`** — create a publisher on a shared connection.
- **`NewConsumer(conn *Connection, opt ConsumerOptions, optionFuncs ...func(*ChannelOptions)) *Consumer`** — create a consumer on a shared connection. *Advisable to use separate connections for Publish and Consume* (see NewConsumer comment).
- **`NewChannel(conn *Conn, optionFuncs ...func(*ChannelOptions)) *Channel`** — create a managed channel (lower-level; most users should use Publisher/Consumer instead).

All three constructors accept variadic `WithOptionFunc` to configure the object.

## Option Patterns

- **`WithConnectionOption*`** and **`WithChannelOption*`** are functional options. Each returns `func(*Options) nil` and mutates the corresponding struct field.
- Key connection options: `WithConnectionOptionContext`, `WithConnectionOptionName`, `WithConnectionOptionDown`, `WithConnectionOptionUp`, `WithConnectionOptionRecovering`, `WithConnectionOptionDelay`, `WithConnectionOptionPassword`, `WithConnectionOptionNotification`.
- Key channel options: `WithChannelOptionContext`, `WithChannelOptionName`, `WithChannelOptionDown`, `WithChannelOptionUp`, `WithChannelOptionRecovering`, `WithChannelOptionDelay`, `WithChannelOptionNotification`, `WithChannelOptionTopology`, `WithChannelOptionProcessor`, `WithChannelOptionNotifyPublish`, `WithChannelOptionNotifyReturn`.
- Publisher options: `WithExchange`, `WithKey`, `WithMandatory`, `WithImmediate`, `WithConfirmationsCount`, `WithContext`, `WithConfirmationNoWait`.
- Consumer options: `WithName`, `WithPrefetchTimeout`, `WithPrefetchCount`, `WithPrefetchSize`, `WithQosGlobal`, `WithQueue`, `WithAutoAck`, `WithExclusive`, `WithNoLocal`, `WithNoWait`, `WithArgs`.

**Important**: ConsumerAutoAck defaults to `false`. Must explicitly call `WithAutoAck(true)` if you want automatic acknowledgment.

## Reconnect / Exponential Backoff

- **`DefaultDelayer`** implements exponential backoff with jitter. Starts at 200ms, doubles each retry. `RetryCap` (default 7, clamped to 7–10) caps the delay exponent, not the attempt count — retries continue indefinitely until the context is cancelled or a recovery callback vetoes them, with the delay saturating at 12.8s–102.4s depending on the cap.
- Configure per-connection with `WithConnectionOptionDelay(delayer)` or per-channel with `WithChannelOptionDelay`.
- The delayer formula: `delay = base * 2^(attempt-1)` with 10% jitter added.
- Context cancellation (`ctx.Done()`) aborts the reconnect loop — always pass a cancelable context.

## Topology & Auto-Recovery

- Use **`WithChannelOptionTopology(topology []*TopologyOptions)`** to declare exchanges/queues once; every declared element is re-declared on connection recovery, durable included (AMQP declares are idempotent for identical parameters; a drifted durable definition surfaces as AMQP 406).
- During reconnection, topology is re-declared via `makeTopology()`; `t.Declare` must be true for any declaration (initial or recovery).
- Exchanges default to `direct` kind; queues declare with the given args/bindings.

## Publisher Confirmations & Deferred Confirms

- **Default confirmation count**: 10 (set via `PublisherUsageOptions.ConfirmationCount`).
- To publish with deferred confirms: use `p.PublishDeferredConfirm(msg)` which returns a `*DeferredConfirmation`, then call `p.AwaitDeferredConfirmation(d, timeout)`.
- **Never mix `Publish` and `PublishDeferredConfirm` on the same channel without understanding the outcome flow** — they use different underlying AMQP methods.
- If `ConfirmationNoWait` is true, confirmation mode is blocked on the channel.

## Consumer QoS & Prefetch

- **Default prefetch count**: 1 (`DefaultConsumerOptions` sets `PrefetchCount: 1`).
- `WithPrefetchCount(n)` sets the QoS prefetch.
- `WithPrefetchSize(size)` is **not supported by RabbitMQ** and seems to block consumers — **avoid using it**.
- `WithQosGlobal(global)` makes QoS global across future channels.
- `WithAutoAck(true)` disables explicit acknowledgment (messages are acked automatically).

## Tracing / Trace Infrastructure

- The `test_env` build tag gates trace instrumentation (files in `internal/traceutils/`).
- When `test_env` is **active**: trace functions (`Confirm`, `Publish`, `Qos`, etc.) send `ParamsTrace` events over a channel stored in the context key `TraceChannelParamsName`.
- When `test_env` is **inactive** (default for production code): these functions are no-ops.
- CI runs `go test -tags test_env` to enable tracing.

## Notifier Channels & Events

- Notifications travel over buffered channels (`chan Event`).
- **Events are dropped if the channel buffer fills** — the `raise` method uses `select` with a `default` case that silently discards events.
- This is intentional for non-blocking operation but means you may miss alerts under high load.
- Always consider whether dropped events are acceptable for your use case.

## Latch / State Management

- The library uses `github.com/LucaWolf/go-notifying-latch` for `NotifyingLatch` operations.
- Latches track `connected` and `managed` / `paused` states internally.
- `AwaitStatus(established bool, timeout time.Duration)` and `AwaitManager(active bool, timeout time.Duration)` are the proper ways to wait for state changes rather than checking `IsClosed()` directly.

## Shutdown / Context Cancellation

- All recovery loops watch `opt.ctx.Done()`. Cancelling the context terminates the reconnect/goroutine loops.
- When you're done: cancel the context (`context.WithCancel`) and call `Close()` on the connection/publisher/consumer.
- Shutdown is idempotent — calling `Close()` multiple times is safe.

## Known Quirks & Gotchas

- Go 1.25.7 is the minimum version — very recent; some language features may be bleeding-edge.
- The library wraps `github.com/rabbitmq/amqp091-go` v1.10.0 and `github.com/michaelklishin/rabbit-hole/v3` v3.2.0.
- `go.work` is NOT used; dependencies are resolved via `go.mod` + `go.sum` only.
- `PublishDeferredConfirm` + `AwaitDeferredConfirmation` is the preferred pattern for end-to-end publish confirmation, but it requires the deferred confirmation object to be kept alive across the timeout/await cycle.
- Consumer `Cancel()` enforces `noWait=false` — the server will be told the consumer is done and messages will be redistributed.
- Topology `Declare` flag: elements with `Declare:false` are skipped entirely (even on initial setup). Use `WithChannelOptionTopology` to ensure topology is created.
- Random consumer names: `RandConsumerName()` generates 8 random hex bytes; `DefaultConsumerOptions()` sets one automatically. If you provide your own name, ensure it's unique per connection.

## What to Check First When Something Feels Off

1. Is the context still alive? Recovery loops die on `ctx.Done()`.
2. Are notifier channels full? Events are silently dropped.
3. Is `test_env` tag needed for tracing-dependent tests?
4. Did you remember `WithAutoAck(true)` for auto-ack consumers?
5. Is the topology `Declare` flag set correctly for your use case?
6. Exponential backoff not slowing down? Check `DefaultDelayer.RetryCap` (default 7, clamped to max 10).
